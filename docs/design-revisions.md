# 設計改訂 — レビュー第2ラウンド

[design-decisions.md](./design-decisions.md) の設計をレビューし、判明した問題と変更点をまとめたものです。

> **この文書は検討の経緯です。** 第3ラウンドを経た確定版は [spec.md](./spec.md) にあります。実装時はそちらを参照してください。画像アップロード（R-2）はこの後に見送りとなるなど、変更された判断が含まれます。

---

## 変更が必要な点

### R-1. 下書きの除外方式 ★最優先

**問題**: `createArticles` 側で `_` 接頭辞を弾く方式では、**下書きの本文がバンドルに残ります**。

実際にデモをビルドして確認済みです。

```
$ grep -o "これはサンプル記事です[^\"]*" demo/dist/assets/index-*.js
これはサンプル記事です。`@fififuchun/article-system` を使うと...
```

`import.meta.glob` は**ビルド時にファイルの中身を JavaScript の文字列として埋め込みます**。`createArticles` の除外はブラウザ上で走る処理なので、配信済みの文字列を「表示しないだけ」であり、開発者ツールから誰でも読めます。

さらに決定的な制約として、**glob パターンはファイルのパスしか見られません**。フロントマターに `draft: true` と書いても、Vite はそれを読めないので除外できません。**バンドル漏れを防ぐ手段はファイル名による除外しかありません。**

これは C-1 で確定した「中身を信じる、ファイル名は付属情報」という方針と矛盾します。しかし物理的な制約なので、方針の側を調整します。

**変更内容**: `_` 接頭辞は維持し、**利用側の glob パターンを変更**します。

```ts
// Before
import.meta.glob("../articles/*.md", { ... })

// After
import.meta.glob("../articles/[!_]*.md", { ... })
```

`[!_]` は「`_` 以外の文字で始まる」という意味です。

**書き忘れ対策**: `createArticles` が `_` 始まりのファイルを受け取ったら、それは glob パターンが誤っている証拠です。開発時に明示的なエラーを出します。

```ts
if (basename.startsWith("_")) {
  console.error(
    "[article-system] 下書きがバンドルに含まれています。" +
    "import.meta.glob のパターンを ../articles/[!_]*.md にしてください"
  );
}
```

除外そのものは glob が行い、`createArticles` は**設定ミスの検出器**として働きます。二重の防御になります。

**代替案**: 下書きを `src/drafts/` に置く方式も成立します（glob の対象外なので確実に漏れない）。公開時にファイルを移動する手間が増えますが、命名規則に依存しない分は堅牢です。将来 GitHub コミット機能が入れば、この移動も Studio 側で自動化できます。

### R-2. 画像アップロード ★設計の骨格に関わる

**決定**: 画像をドラッグ&ドロップしたらアップロードされる（GitHub のコメント欄と同じ体験）。

**これは「将来やる」としていた GitHub コミット機能を v1 に前倒しすることを意味します。**

静的サイトには画像の保存先がありません。GitHub のコメント欄が動くのは、裏に GitHub のアセットサーバーがあるからです。同じ体験を作るには保存先が必要です。

#### 保存先の選択肢

| 方式 | 仕組み | 必要なもの |
| --- | --- | --- |
| **GitHub Contents API** | リポジトリの `public/article_imgs/` に直接コミット | リポジトリ書き込み権限のトークン |
| 外部画像ホスト | Cloudinary / Vercel Blob などへアップロード | 各サービスのAPIキー |
| 自前のAPI | Vercel Functions などを立てる | バックエンドの実装 |

**GitHub Contents API を推奨します。** 画像が記事と同じリポジトリに入るため管理が一元化され、追加のサービス契約も不要です。そして同じ仕組みで md 本体もコミットできるようになります。

#### 連鎖する変更

**1. ホスティング認証が「任意」から「必須」に変わる**

決定#11 では「秘匿は利用側の責務、ライブラリは認証を持たない」としました。**この方針自体は維持します**が、位置づけが変わります。

トークンをブラウザに置く以上、Studio のページが無防備だとリポジトリへの書き込み権限が公開されます。README で「任意」ではなく**「必須」として案内**します。Vercel Deployment Protection や Cloudflare Access などのホスティング側認証が前提になります。

トークンは対象リポジトリのみ・contents 書き込みのみに絞った fine-grained PAT を使い、影響範囲を最小化します。

**2. A-3（リロードで画像が消える問題）が自動的に解決する**

アップロードされた画像は実在するURLを持つため、blob URL のようにリロードで無効化されません。localStorage から復帰しても画像は生きています。**「仕方ない」とした問題が消えます。**

**3. 「md をダウンロード」の位置づけが変わる**

画像を GitHub にコミットできるなら、md も同じ仕組みでコミットできます。ダウンロードは**フォールバック手段**（トークン未設定時、あるいはローカル保管用）という位置づけに後退します。

**4. 検証項目から「未登録の画像を参照」が消える**

アップロード時点で実在が保証されるため、この検証は不要になります。既存画像を参照できずブロックされる問題（A-2）も同時に消えます。

**5. アップロード画像のファイル名衝突**

同名の画像を2回アップロードすると既存が上書きされます。GitHub は UUID を振ることで回避しています。

読める名前を保ちたい場合は、衝突時に連番を付ける（`art_0.webp` → `art_0-2.webp`）方式を採ります。ファイル名を確認できるので、こちらを推奨します。

#### 段階的な実装

一度に全部やる必要はありません。

1. **v1.0** — ドロップした画像はブラウザ内プレビューのみ、md はダウンロード（現行案）
2. **v1.1** — トークンを設定すると画像が GitHub にアップロードされる
3. **v1.2** — md 本体も GitHub にコミットできる

v1.0 の時点で「アップロード先を差し替えられる形」にしておけば、後続はその実装を埋めるだけです。

```tsx
<ArticleStudio
  uploadImage={async (file) => { /* 返り値は画像URL */ }}
/>
```

アップロード処理を prop で受け取る形にすれば、**ライブラリは GitHub にも外部ホストにも縛られません**。`renderLink` でルーターを利用側に委ねた設計と同じ思想です。

### R-3. `articles` を v1 から受け取る

**変更内容**: `<ArticleStudio articles={articles} />` を v1 から前提にします。

前回「既存画像の参照も articles を知らないことに起因する」と書きましたが、これは不正確でした。既存画像の一覧と記事一覧は別物です。訂正します。

`articles` が実際に必要なのは以下です。

| できること | 実害の大きさ |
| --- | --- |
| **ファイル名衝突の検出** | **大** — 同名ファイルを置くと既存記事が物理的に消える |
| 日付衝突の警告 | 大 — 過去日付で書くと公開済みURLが全部ずれる |
| 次の `id` の予告 | 中 — 公開するまで自分のURLが分からない |
| 一覧プレビューで他の記事と並べる | 小 |
| 既存記事の編集（v2） | v2 の前提 |

C-1 で「ファイル名は付属情報」と決めましたが、**同名ファイルは既存記事を物理的に上書きします**。付属情報であっても衝突は実害を生みます。

利用側の負担は1行だけです。すでに `src/lib/articles.ts` を作らせている以上、追加の手間はほぼありません。

### R-4. デフォルトCSSは `:where()` で書く

**問題**: `.as-heading` と利用側の `.my-heading` は**詳細度が同点**です。同点の場合は CSS ファイル内で後に定義された方が勝つため、読み込み順によって上書きが効いたり効かなかったりします。Vite のコード分割や HMR で順序は変わりえます。

**変更内容**: デフォルトCSS側を `:where()` で包み、詳細度を0にします。

```css
/* Before */
.as-heading { font-size: 1.5rem; }

/* After */
:where(.as-heading) { font-size: 1.5rem; }
```

`:where()` は中身の詳細度を強制的に0にします。**利用側のどんなクラスにも必ず負ける**ため、読み込み順に関係なく上書きが常に効きます。

書き方が変わるだけでコストはありません。最初からこの形で書き始めます。

### R-5. 起動時のテンプレート表示

**決定**: フロントマターのテンプレートが最初から入った状態で始めます（C-5）。スマホで `---` やキー名を打つ苦痛を避けるためです。

```markdown
---
title:
date: 2026-08-21
latestUpdate: 2026-08-21
staff:
thumbnail:
---

## 見出し

本文をここに書きます。
```

`date` と `latestUpdate` には今日の日付が入った状態にします。`staff` は毎回入力する方針（C-6）なので空にします。

#### 決めておく必要がある分岐

**復帰する下書きがある場合はテンプレートを出しません。** 保存内容を上書きしてしまうためです。

```
localStorage に下書きがある → 下書きを復帰
localStorage が空           → テンプレートを表示
```

不要な記載は Ctrl+A で選択して消す運用（B-4）です。**全部消して空になった場合、テンプレートは再挿入しません。** 意図的に消したものを勝手に戻すと操作を奪うことになります。代わりに「テンプレートを挿入」ボタンを用意します。

#### テンプレートと厳格検証の相互作用

プレースホルダを `title: 記事タイトルをここに書く` のような文字列にすると、**検証を通ってしまいます**。値が入っているためです。雛形のまま公開される事故が起きます。

そのため上記のテンプレートは**値を空にしてあります**。空なら必須項目の欠落として検証が止めます。

### R-6. `date` と `latestUpdate` の意味を確定する

**決定**（C-2）:

| フィールド | 意味 | 新規作成時の初期値 | 既存記事の編集時（v2） |
| --- | --- | --- | --- |
| `date` | **公開日** | 今日 | 変更しない |
| `latestUpdate` | **最終編集日** | 今日（= `date` と同じ） | 今日に更新 |

新規作成時は両方とも今日になります。既存記事を編集したときだけ `latestUpdate` が動きます。

---

### R-7. 未来日の扱い ★新規に発見

**問題**: `date` を公開日と定義しましたが、**未来の日付を書いても即座に一覧へ出ます**。`createArticles` は日付でフィルタしないためです。予約投稿のつもりが即公開になります。

3つの選択肢があります。

| 方式 | 挙動 | 備考 |
| --- | --- | --- |
| **検証で弾く**（推奨） | 未来日を書くとダウンロード不可 | 予約投稿は元々できないので、誤解を生まない |
| 未来日は非表示 | `createArticles` が今日より後の記事を除外 | 予約投稿として機能するが、ビルドし直さないと公開されないので実質使えない |
| 何もしない | 未来日でも即公開 | 「公開日」という名前と挙動が食い違う |

**検証で弾く方式を推奨します。** 静的サイトは再ビルドしないと内容が変わらないため、日付を未来にしても自動公開はされません。**予約投稿は原理的に実現できない**ので、できるかのように見せない方が誠実です。

### R-8. README への追記

**GitHub インストールのバージョン規律**（C-4）

```bash
# 推奨: タグで固定する
npm i github:fififuchun/article-system#v0.2.0

# 非推奨: 常に最新を取る（npm update で意図せず更新される）
npm i github:fififuchun/article-system
```

`package-lock.json` にコミットハッシュが記録されるため通常は固定されますが、`npm update` を実行すると最新が来ます。複数プロジェクトで使っている状態で破壊的変更を入れると、あるプロジェクトの `npm install` のタイミングで壊れます。

**併せて追記する項目**

- `import.meta.glob` のパターンは `[!_]*.md` にすること（R-1）
- Studio を本番に置く場合、ホスティング側の認証が必須であること（R-2）
- `styles.css` の import 方法と、読み込まない場合の挙動

### R-9. Studio のエントリポイント分離は後回し

前回「実装前に決着が必要」と書きましたが、**過大評価でした。格下げします。**

現在のバンドル 307KB のうち 156KB は react-markdown 系で、これは読者向けの `ArticleDetail` が使うため Studio の有無に関わりません。Studio 固有で増えるのは十数KB程度（gzip 後は数KB）と見積もられます。

個人ブログの規模では実質的な影響はありません。**画像アップロードや GitHub API クライアントを載せて Studio が育った段階で対応すれば間に合います。**

## 実装順序（改訂）

R-1 と R-4 は他のすべてに影響するため最初に片付けます。

1. **glob パターンの変更と `createArticles` の警告実装**（R-1）— 漏れは早く塞ぐ
2. **バリデータの切り出しとテスト** — 未来日の検出（R-7）を含む
3. **`createArticles` の改修** — 不正な日付の扱い、`_` の検出
4. **表示コンポーネントの修正** — 見出しタグ、`<p>` の入れ子、画像パス、`as-` クラス付与
5. **`styles.css` の作成** — 最初から `:where()` で書く（R-4）
6. **アイコンセット**
7. **`ArticleStudio` v1.0** — `articles` を受け取る（R-3）、テンプレート表示（R-5）、`uploadImage` prop の口だけ用意（R-2）
8. **画像アップロードの実装**（R-2 の v1.1）
9. **配布まわり** — `exports` 追加、pre-commit フック、README 改訂（R-8）
