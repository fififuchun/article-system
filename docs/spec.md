# @fififuchun/article-system 仕様書

この1枚が設計の確定版です。実装に必要な内容はすべてここに含まれています。

`design-decisions.md` と `design-revisions.md` は検討の経緯を残した記録であり、読む必要はありません。内容が食い違う場合はこの文書が優先します。

---

## 1. このライブラリは何か

**記事を書く側に提供する道具です。**

マークダウンを書いて記事にするまでの流れ — 書く、確認する、検証する、md として取り出す — を丸ごと引き受け、複数のプロジェクトで毎回作り直さずに済ませることが目的です。

読者向けの表示コンポーネント（`ArticleList` / `ArticleDetail`）も提供しますが、これらは **Studio のプレビューが本番と一致することを保証する土台**という位置づけです。

### 前提条件

- **Vite + React** プロジェクトであること（`import.meta.glob` に依存するため）
- **TypeScript** を使用していること
- React 18 以上

### 提供するもの

| 種別 | 名前 | 役割 |
| --- | --- | --- |
| 関数 | `createArticles` | md の文字列群から `Article[]` を生成する |
| 関数 | `validateArticle` | md の文字列を検証して問題の一覧を返す |
| コンポーネント | `ArticleStudio` | 執筆・プレビュー・検証・md 出力を行う画面 |
| コンポーネント | `ArticleDetail` | 記事詳細の表示 |
| コンポーネント | `ArticleList` | 記事一覧の表示 |
| スタイル | `styles.css` | そのまま公開できる完成度のデフォルトCSS |
| アイコン | 各種 | インライン SVG のアイコンセット |

```
your-project/
├── src/
│   ├── articles/
│   │   ├── 2026-08-22-夏の更新.md
│   │   └── _2026-08-23-書きかけ.md    ← 下書き（公開されない）
│   ├── lib/
│   │   └── articles.ts                ← 記事データの生成
│   └── pages/
│       ├── BlogList.tsx
│       ├── BlogDetail.tsx
│       └── BlogStudio.tsx
└── public/
    └── article_imgs/
        ├── art_0.webp
        └── art_1.webp
```

### 記事データの生成

```ts
// src/lib/articles.ts
import { createArticles } from "@fififuchun/article-system";

const rawFiles = import.meta.glob("../articles/[!_]*.md", {
  query: "?raw",
  import: "default",
  eager: true,
}) as Record<string, string>;

export const articles = createArticles(rawFiles);
```

**`[!_]` は必須です。** 理由は第4章で説明します。

`import.meta.glob` は Vite のビルド時処理のため、ライブラリ側ではなく利用側に書く必要があります。

### ルーティング

```tsx
import { Routes, Route } from "react-router-dom";

<Routes>
  <Route path="/blog" element={<BlogList />} />
  <Route path="/article/preview" element={<BlogStudio />} />
  {/* :slug より前に定義する */}
  <Route path="/blog/:slug" element={<BlogDetail />} />
</Routes>
```

Studio を本番に置くかどうかは利用側が決めます。ライブラリは認証を持ちません。

```tsx
{import.meta.env.VITE_STUDIO === "1" && (
  <Route path="/article/preview" element={<BlogStudio />} />
)}
```

## 3. データモデル

### Article 型

```ts
interface Article {
  slug: string;         // URL に使う識別子。記事の身元
  filename: string;     // 拡張子付きファイル名
  title: string;
  date: string;         // "YYYY-MM-DD" 公開日
  latestUpdate: string; // "YYYY-MM-DD" 最終編集日
  staff: string;        // 担当者名
  thumbnail: string;    // ファイル名のみ（パスなし）
  content: string;      // フロントマターを除いた本文
}
```

**`id` は廃止しました。** 日付昇順の index を URL に使っていたため、**既存記事より古い日付の記事を後から足すと、以降のすべての URL が別の記事を指していました**。エラーも警告も出ずに静かにずれるため、いちばん重い問題でした。

並び順が必要なときは配列の位置を使ってください。`createArticles` は `date` 昇順で返します。

### slug の決まり方

1. フロントマターに `slug` があればそれを使う
2. 無ければ**ファイル名から拡張子を除いたもの**を使う（既存記事のための後方互換）

```
slug: summer-update を書いた            → slug = "summer-update"
書いていない / 2026-08-23-夏の更新.md    → slug = "2026-08-23-夏の更新"
```

**Studio は雛形に `slug:` を自動で入れます**（既定は日付）。新しく書く記事は何もしなくても
`slug: 2026-08-23` が入るため、**URL に日本語が入りません**。

```
myblog.com/blog/2026-08-23
```

英語の URL にしたい記事だけ、その行を書き換えます（`slug: summer-update`）。

**ファイル名は日本語のままにします。** リポジトリでファイルを探すときに見つけやすく、
URL とは切り離されているので影響しません。

同じ日に2本書くときは、Studio が `articles` を見て `2026-08-23-2` を雛形に入れます。
**一度ファイルに書かれた slug は動きません。** `id` のように後からずれることはありません。

既存記事（`slug:` の無い記事）は**ファイル名が URL になります**。日本語を避けたい場合は
その記事に `slug:` を書き足してください。書き足すと URL が変わる点には注意が必要です。

**slug は記事の身元です。** 変えると公開済みの URL が切れます。ファイル名を変えるときは、URL を保つために `slug:` を明示してください。

日本語をそのまま使えます。URL に載せるときは利用側で `encodeURIComponent` を通してください。

**同じ slug の記事が2つあると、片方が開けません。** `createArticles` が `console.warn` で知らせます（例外は投げません — 記事が読めなくなるわけではないため。spec §5）。

### フロントマター

```markdown
---
title: 記事タイトル
slug: 2026-08-23
date: 2026-08-23
latestUpdate: 2026-08-23
staff: 田中 花子
thumbnail: art_0.webp
---

## 見出し

本文...
```

| フィールド | 型 | 必須 | 意味 |
| --- | --- | --- | --- |
| `title` | string | ✔ | 記事タイトル |
| `date` | YYYY-MM-DD | ✔ | **公開日**。並び順に使う |
| `latestUpdate` | YYYY-MM-DD | ✔ | **最終編集日**。一覧カードに表示される |
| `staff` | string | ✔ | 担当者名 |
| `thumbnail` | string | ✔ | サムネイル画像のファイル名 |
| `slug` | string | | URL に使う識別子。Studio が日付を自動で入れる。省略するとファイル名から作る |

`slug` 以外は必須です。欠けると検証で止まります。

**新規作成時は `date` と `latestUpdate` の両方が今日になります。** 既存記事を編集したときだけ `latestUpdate` が動きます（v2 の機能）。

**未来日も許可します。** 静的サイトは再ビルドしないと内容が変わらないため予約投稿にはなりませんが、書くこと自体は止めません。

### slug に使えない文字

URL のパスとして成立しない文字は検証で止めます。

- `/` — パスが割れる
- `?` `#` — クエリとフラグメントの区切り
- 空白
- 前後の `.`、`.` だけ、`..` だけ

ファイル名から作る場合はこれらが入りません（`buildFilename` が除いています）。手で `slug:` を書いたときのための検証です。

### フロントマターのパース仕様

自前実装です。YAML ではありません。

```ts
function parseFrontmatter(raw: string): {
  data: Record<string, string>;
  content: string;
}
```

`---` で囲まれたブロックを行ごとに読み、**最初のコロン**で key と value に分けます。

| 記法 | 結果 |
| --- | --- |
| `title: 記事：その1` | ✅ 値の中のコロンは安全 |
| CRLF 改行 | ✅ 正しく処理される |
| `title: "記事"` | ❌ 引用符が値に含まれる → 検証で止める |
| `tags: [a, b]` | ❌ 文字列 `"[a, b]"` になる（配列にならない） |
| 複数行の値 | ❌ 2行目以降は無視される |
| `# コメント` | ❌ コロンがない行として読み飛ばされる |

フロントマターが無い場合は例外を投げず `{ data: {}, content: raw }` を返します。Studio で入力途中の壊れたテキストでもクラッシュしないためです。

## 4. 下書きの扱い ★実装上もっとも注意が必要

### 仕組み

下書きは**ファイル名の `_` 接頭辞**で区別します。

```
src/articles/
  _2026-08-23-書きかけの記事.md   ← 下書き
  2026-08-22-夏の更新.md          ← 公開
```

### なぜ glob パターンで除外しなければならないのか

`import.meta.glob` は**ビルド時にファイルの中身を JavaScript の文字列として埋め込みます**。

```js
// ビルド後の dist/assets/index.js（イメージ）
{
  "../articles/2026-08-22-夏の更新.md": "---\ntitle: 夏の更新\n...本文全部...",
  "../articles/_2026-08-23-書きかけ.md": "---\ntitle: 書きかけ\n...本文全部...",
}
```

`createArticles` の中で除外しても、それはブラウザ上で走る処理です。**下書きの本文はすでに配信済み**であり、開発者ツールから誰でも読めます。

そして glob パターンは**ファイルのパスしか見られません**。フロントマターに `draft: true` と書いても Vite はそれを読めないため除外できません。

**glob パターンによる除外が唯一の手段です。**

```ts
import.meta.glob("../articles/[!_]*.md", { ... })
```

### 混入時は例外を投げる

`createArticles` が `_` 始まりのファイルを受け取ったら、glob パターンが誤っている証拠です。**開発・本番を問わず例外を投げてページを停止させます。**

```ts
if (basename.startsWith("_")) {
  throw new Error(
    `[article-system] 下書きファイル "${basename}" がバンドルに含まれています。\n` +
    `本文が公開されています。import.meta.glob のパターンを\n` +
    `  "../articles/[!_]*.md"\n` +
    `に変更してください。`
  );
}
```

例外を投げても漏洩自体は取り消せません（すでに配信済みのため）が、**壊れたサイトが最も確実な警報**として機能し、放置される期間を最短にします。エラーメッセージには原因と直し方を必ず含めます。

## 5. createArticles

```ts
function createArticles(rawFiles: Record<string, string>): Article[]
```

### 処理

1. `Object.entries()` でファイルパスと中身を取得する
2. `_` 始まりのファイルがあれば例外を投げる（第4章）
3. 各ファイルの フロントマターをパースする
4. 検証を行い、問題があれば `console.warn` で出す
5. `date` 昇順（古い順）でソートする
6. `slug` を決める（フロントマター優先、無ければファイル名から）。重複していれば console.warn

### 実装上の注意

**不正な日付でソートが壊れないようにします。** `new Date()` の比較で `NaN` が返ると `Array.prototype.sort` の結果は仕様上保証されません。実測でも順序が崩れます。

```
入力:  ["x", "2026-01-01", "2025-01-01"]
結果:  x, 2025-01-01, 2026-01-01     ← "x" が先頭に居座る
```

`YYYY-MM-DD` は辞書順と時系列順が一致するため、**文字列比較でソートします**。これで `NaN` が発生しません。

### 並び順

`date` 昇順（古い順）です。一覧を新しい順にしたい場合は利用側で反転します。

```tsx
<ArticleList articles={[...articles].reverse()} … />
```

`.reverse()` は破壊的なのでスプレッドでコピーしてから呼びます。`slug` は並び順に依存しないので URL は壊れません。

## 6. バリデータ

Studio と `createArticles` の両方から使う独立した部品です。

```ts
interface Issue {
  level: "error";
  field?: string;
  message: string;
}

function validateArticle(
  raw: string,
  context?: {
    articles?: Article[];   // ファイル名衝突の検出用
    filename?: string;      // 検証対象のファイル名
  }
): Issue[]
```

### 検証ルール

| 検出内容 | 例 | 放置した場合に起きること |
| --- | --- | --- |
| 必須項目の欠落 | `latestUpdate` がない | `0年undefined月undefined日` と表示される |
| キー名の typo | `lastUpdate` と書いた | 同上。無言で通過する |
| 日付の形式違反 | `date: 2026/08/23` | 並び順が壊れる |
| 引用符付きの値 | `title: "記事"` | 引用符ごと値に入る |
| フロントマターの閉じ忘れ | `---` が片方だけ | 全文が本文として扱われる |
| 更新日が投稿日より前 | `latestUpdate < date` | 論理矛盾 |
| 画像が見つからない | typo したファイル名 | 本番で壊れた画像になる |
| ファイル名の衝突 | 既存と同名 | 既存記事が物理的に上書きされ消える |

**未来日は検証しません。** 許可する方針のためです。

キー名の typo は、既知のフィールド名との編集距離が近い未知キーを検出して「`latestUpdate` の誤りでは」と示します。

### 画像の存在確認

ファイル一覧を受け取るのではなく、**実際に読み込んで確かめます**。

```
手書きの art_0.webp
  → imageBasePath + ファイル名 で画像の読み込みを試す
  → 成功 = リポジトリに実在する → 問題なし
  → 失敗 = 名前の間違い、または未配置 → エラー

失敗の原因は2つあります。**文言では両方を示します。** 名前が合っていても、
まだ画像を置いていないだけの場合があるためです（リロード後は仮登録が消えます）。

ドロップした画像
  → blob URL で表示。サーバーに無いのは当然なので検証対象外
  → 本番ダウンロード時の「配置してください」一覧へ
```

設定が増えず、既存画像の使い回しもでき、typo も捕まえられます。

**実装上の注意**: SPA のフォールバック設定によっては存在しないパスでも `index.html` が 200 で返ります。ステータスコードではなく `<img>` の `onError` で判定してください。

## 7. ArticleDetail

```tsx
<ArticleDetail

  dateLabel="最終更新日時"           // 既定値
  classNames={{ ... }}              // 任意

```

### Props

| prop | 型 | 必須 | 既定値 |
| --- | --- | --- | --- |
| `article` | `Article` | ✔ | — |
| `imageBasePath` | `string` | | `"/article_imgs/"` |
| `dateLabel` | `string` | | `"最終更新日時"` |
| `classNames` | `ArticleDetailClassNames` | | `{}` |

記事が見つからない場合のハンドリングはありません。利用側でガードします。

### DOM 構造

```html
<div class="as-article">
  <div class="as-header">
    <div class="as-date">
      <p class="as-date-year">2026</p>
      <p class="as-date-day">8/23</p>
    </div>
    <p class="as-title">記事タイトル</p>
  </div>

  <div class="as-latest-update">
    <svg class="as-date-icon">…</svg>
    <span>最終更新日時 2026年8月23日</span>
  </div>

  <img class="as-thumbnail" src="/article_imgs/art_0.webp">

  <!-- 本文（react-markdown の出力） -->
  <h2 class="as-heading">見出し</h2>
  <p  class="as-paragraph">本文...</p>
  <div class="as-image"><img src="/article_imgs/art_1.webp"></div>

  <p class="as-footer">担当：田中 花子</p>
</div>
```

### マークダウンの対応

| 記法 | 出力 |
| --- | --- |
| `##` | `<h2 class="as-heading">` |
| `###` | `<h3 class="as-subheading">` |
| `####` | `<h4 class="as-subsubheading">` |
| 段落 | `<p class="as-paragraph">` |
| `![](file.webp)`（画像だけの行） | `<div class="as-image"><img>` |
| 文中の画像（テキストと混在） | `<p>` の中にインラインの `<img>`。GitHub のマークダウンに準拠する |
| 単一改行 | `<br>`（remark-breaks） |
| 表・取り消し線・タスクリスト | 素の HTML 要素（remark-gfm）。CSS は子孫セレクタで当てる |
| リスト・引用・コードブロック | 同上 |
| 生の HTML | 無効。文字列としてエスケープされる |

`rehype-raw` を入れないため、**記事経由の XSS は構造的に防がれています**。

### 現行実装から修正する点

**1. 見出しを正しいタグで出力する**

```tsx
// Before — すべて div
h2: ({ children }) => <div className={classNames.heading}>{children}</div>,

// After
h2: ({ children }) => <h2 className={cx("as-heading", classNames.heading)}>{children}</h2>,
```

現在は `<div>` で出力しているため、スクリーンリーダーの見出しジャンプが効かず、検索エンジンも文書構造を読めません。デフォルトCSS側でブラウザ標準スタイルをリセットするので、見た目は変わりません。

**記事タイトルは `<p>` のままとし、`<h1>` は持ちません。** 本文の見出しが `<h2>` から始まるのを正常とします。CSS でタイトルが `h2` より大きく見えるよう階層を作ります。

**2. `<p>` の中に `<div>` が入る問題を解消する**

マークダウンでは画像だけの行も段落として扱われるため、現在の出力は不正な入れ子になっています。

```html
<div class="article-paragraph">
  <p><div class="article-image"><img></div></p>   ← 不正
</div>
```

CSR では動きますが、React 開発モードで `validateDOMNesting` 警告が出ます。SSR ではブラウザが `<p>` を自動で閉じ、ハイドレーションエラーになります。

段落のラッパーを1段（`<p class="as-paragraph">`）にし、画像は `<p>` でラップしません。

**3. その他**

| 項目 | 対処 |
| --- | --- |
| `thumbnail` が空でも `<img>` が出る | 未指定なら描画しない |
| 外部URLの画像が使えない | 絶対URL（`http://` `https://` `//` 始まり）は `imageBasePath` を前置せず素通し |
| 本文の `blob:` 画像が消える | `urlTransform` で画像の `src` だけ通す（下記） |

#### 本文の `blob:` を通す ★調査済み

react-markdown の既定の `urlTransform` は、**http / https / mailto / tel 以外の
プロトコルを空文字にします**。Studio がプレビューで差し替える `blob:` URL もこれに
当たるため、何もしないと**ドロップした画像が本文に出ません**。空文字に `imageBasePath`
が前置され、`src="/article_imgs/"` だけが残ります。

サムネイルは `<img>` を自分で描くので影響を受けません。**本文だけが出ない**という
分かりにくい形で壊れます。

通すのは **画像の `src` だけ**です。リンクの `href` は既定のまま潰します。`javascript:`
を通すと、本文を書けるだけでスクリプトを走らせられます（`rehype-raw` を入れない判断と
同じ理由。§17）。

**テストは描画された `src` を見ます。** md の文字列だけを見ていたため、この壊れ方に
長いあいだ気づけませんでした。

## 8. ArticleList

```tsx
<ArticleList
  articles={articles}
  imageBasePath="/article_imgs/"
  getArticleUrl={(article) => `/blog/${encodeURIComponent(article.slug)}`}
  renderLink={(url, children, key) => <Link key={key} to={url}>{children}</Link>}
  classNames={{ ... }}
/>
```

### Props

| prop | 型 | 必須 | 既定値 |
| --- | --- | --- | --- |
| `articles` | `Article[]` | ✔ | — |
| `getArticleUrl` | `(article) => string` | ✔ | — |
| `renderLink` | `(url, children, key) => ReactNode` | ✔ | — |
| `imageBasePath` | `string` | | `"/article_imgs/"` |
| `classNames` | `ArticleListClassNames` | | `{}` |

`renderLink` でリンク要素の生成を利用側に委ねているため、**ルーターに一切依存しません**。React Router でも Next.js の `Link` でも素の `<a>` でも動きます。

返す要素に `key={key}` を付けるのは利用側の責任です。

カードに表示する日付は `latestUpdate` です。

### DOM 構造

```html
<div class="as-grid">
```

## 9. ArticleStudio

### 接続

```tsx
// src/pages/BlogStudio.tsx
import { ArticleStudio } from "@fififuchun/article-system";
import { articles } from "../lib/articles";

export default function BlogStudio() {
  return <ArticleStudio articles={articles} storageKey="my-blog" />;
}
```

### 設置方法（ArticleStudioRoute）

利用側がページを作って `<Route>` を定義する手間を無くします。`App.tsx` に1行置くだけです。

```tsx
// App.tsx
<>
  <YourRoutes />
  <ArticleStudioRoute articles={articles} github={{ repo: "me/blog" }} />
</>
```

**ハッシュが `#/studio` のときだけ画面を占有し、それ以外では何も描画しません。**
だから置き場所はどこでも構いません。`hashPath` で変更できます。

#### なぜハッシュか

`#` より後ろは**サーバーに送られず、react-router の `<Route path>` も見ません**。
つまり利用側のルーティング設定に手を入れずに済みます。これが「追加1行」の理由です。

読者向けの一覧・詳細は**実パスのまま**にします。ハッシュだとクローラーから見て全ページが
同じ1ページになり、記事ごとに検索結果へ載りません。**執筆画面は自分しか開かないので
ハッシュで困りません。**

#### なぜ全画面で覆うか

Studio は左右2ペインで高さいっぱいを使うグリッドです。利用側の `<main style={{ maxWidth: 840 }}>`
の中に流れると、エディタとプレビューが各420pxになって使えません。
**覆えば置き場所が結果に影響しません。**

**利用側のヘッダーとフッターは隠れます。** モーダルで開いたダイアログは背後のすべてを
`inert` にするため、ヘッダーだけ操作可能に残すことはできません。元の画面へは × か Esc で
戻ります。

ヘッダーの下に出す形も検討しましたが採りませんでした。利用側に `--as-studio-header-top` の
指定を要求することになり、`z-index` の勝負と Esc の自前実装も戻ってくるためです。
埋め込みたい場合は `ArticleStudio` を直接使えます。

#### `<dialog>` を使う

`z-index` の数字で殴ると、利用側がもっと大きい値を使っていたときに負けます。
`<dialog>` を `showModal()` で開くと**トップレイヤー**に移り、通常の `z-index` とは
別勘定になるため確実に最前面を取れます。あわせて3つが付いてきます。

- **Esc で閉じる**（自前の実装が要らない）
- **背後が `inert` になる** — 後ろのナビをクリックできず Tab も入らない
- **`::backdrop`** で背後を暗くできる

**Esc で閉じたときはハッシュを戻します。** 戻さないと「画面は閉じたのに URL は `#/studio`」
という食い違いが残ります。

#### 閉じるボタンは操作帯に重ねない

× は**自分の帯**を持ちます。dialog を縦積みにして、1段目に閉じるボタンの帯、2段目に
Studio を置きます。

```
┌──────────────────────────────── × ┐ ← 閉じるボタンの帯（sticky, top: 0）
├─ 投稿 │ 下書きDL │ 新しく書く ── 詳細│一覧┤ ← 操作帯（sticky, top: 帯の高さ）
│                   │                 │
```

当初は操作帯の右上に 2.5rem の正方形を重ねていました。**操作帯の高さはボタンの文字サイズ
と余白で決まるため、2.5rem と一致する保証がありません。** 一致しないと × がはみ出し、
罫線がペインに食い込んで形が崩れます。「一覧」タブが押せなくなるのを `padding-right: 2.5rem`
で防いでいたのも、同じ数字の一致に依存していました。

重ねるのをやめると、`--as-studio-header-top` を帯の高さにするだけで操作帯がその下に
貼り付きます。**帯の高さがどう変わっても × は正方形のままです。**

#### 本番に含める

スマホから書けることを優先します（§9）。遅延読み込みには**しません** — 削れるのは
gzip で8KB程度で、実装を単純に保つほうが得だと判断しました。

誰でも `#/studio` を開けますが、**トークンが無ければ編集画面は出ません**（§15）。

#### 直接使う道も残す

自分のルーティングに埋め込みたい場合は `ArticleStudio` を今までどおり使えます。
その場合は `--as-studio-header-top` で操作帯のオフセットを調整します（§9 レイアウト）。

### Props

```ts
interface ArticleStudioProps {
  articles: Article[];        // 衝突検出・一覧プレビュー用。**必須**
  storageKey?: string;        // localStorage の保存先を分ける
  imageBasePath?: string;     // 既定 "/article_imgs/"
  dateLabel?: string;         // 既定 "最終更新日時"
  classNames?: ArticleStudioClassNames;
  articleClassNames?: ArticleDetailClassNames;
  github?: GitHubConfig;      // 渡すとダウンロードではなくコミットになる（§15）
}
```

**v1 は新規作成専用**ですが、内部状態は「白紙から書く」ではなく**「編集中の記事」**としてモデル化します。既存記事編集（v2）は初期値を差し替えるだけで実現できる形にしておきます。

### レイアウト

操作は**上端の帯に集めます**。左に md を出す操作、右に何を見るかの切り替えを置きます。

```
PC（左右2ペイン）
┌─ 投稿/本番DL │ 下書きDL │ 新しく書く ──────── 詳細 │ 一覧 ┐ ← sticky
├──────────────────────┬────────────────────────────┤
│ ⚠ 検証エラー（押したとき）│                            │
│ ---                  │   2026                     │
│ title: ...           │   8/23 │ 記事タイトル          │
│ ---                  │   ────────                 │
│ ## 見出し             │   見出し                    │
│ 本文...               │   本文...                   │
│                      │                            │
│ 画像 [名前][↓]        │                            │
└──────────────────────┴────────────────────────────┘
                  罫線1本で区切る（隙間は空けない）

スマホ（上下2ペイン）
┌──────────────────────┐
│ 投稿 │ 下書きDL │ 新規 │  ← 帯は解体。sticky にしない
├──────────────────────┤
│ ⚠ 検証エラー           │
│ textarea             │
│ 画像 [名前][↓]         │
├──────────────────────┤
│ 詳細 │ 一覧            │  ← 切り替え対象の直前に戻す
│ プレビュー              │
└──────────────────────┘
```

**検証エラーは textarea の上**に出します。押したボタンの真下に出るため見落としません。textarea は高さがあるので、下に置くと画面外に出て「何も起きていない」ように見えます。

**ペインのあいだは罫線1本**で、隙間は空けません。textarea も角丸と枠線を持たず、ペインいっぱいに広がります。ボタンも角丸を持たず、罫線で区切った一続きの帯にします。

左の3つのボタンは**帯の幅を埋めます**（`flex: 1 1 auto`）。中身の幅のままだと、画面が広いときに「新しく書く」の右に隙間が開き、最後のボタンの罫線がペイン間の罫線とずれた位置で宙に浮きます。`flex-basis` は `auto` のままにして余りだけを等分します。等分にすると「投稿」が無駄に広くなり、文言の長さの差が消えます。

帯は `position: sticky` で上端に留まります。利用側にも固定ヘッダーがある場合は CSS 変数でずらせます。

```css
:root { --as-studio-header-top: 52px; }  /* 利用側のヘッダー高さ */
```

### 編集ペイン

**生の md を1枚の textarea で編集します。** フォーム化しないことで、エディタとのコピーペーストが自由に行き来でき、ファイルの中身と 1:1 が保たれます。

### 起動時のテンプレート

localStorage が空のとき、この内容を初期表示します。

```markdown
---
title:
date: 2026-08-23
latestUpdate: 2026-08-23
staff:
thumbnail:
---

## 見出し

本文をここに書きます。
```

`date` と `latestUpdate` には今日の日付を入れます。`staff` は毎回入力する方針のため空にします。

**プレースホルダの値は入れません。** `title: 記事タイトルをここに書く` のような文字列を入れると値が入っていることになり検証を通ってしまうため、雛形のまま公開される事故が起きます。

**復帰する下書きがある場合はテンプレートを出しません。** 保存内容を上書きしてしまうためです。

**「新しく書く」ボタンで明示的にテンプレートへ戻せます。** 押すと確認を挟み、承諾されたときだけ今日の日付の雛形に置き換えます。自動では決して消しません。

Ctrl+A で全消しして空になっても、**テンプレートは自動で再挿入しません**。意図的に消したものを勝手に戻すと操作を奪うことになるためです。

### プレビューペイン

タブで2種類を切り替えます。

| タブ | 内容 |
| --- | --- |
| **詳細** | `ArticleDetail` をそのまま描画 |
| **一覧** | `ArticleList` に**直近6件**を渡す。日付の新しい順。**編集中の記事は必ず含める**（過去日を書いても消えないように） |

一覧プレビューは既存記事に混ぜて表示します。隣の記事と並べることで、タイトルの折り返しやサムネイルの雰囲気を比較できます。**編集中の記事のカードには URL の予告を出します。** 出したあとどの URL で公開されるかが、書いている最中に分かります。

タイトルの折り返しやサムネイルのトリミングは**詳細プレビューでは絶対に気づけない**ため、両方を確認できるようにします。

`ArticleDetail` / `ArticleList` をそのまま再利用することで、**プレビューと本番の一致が構造的に保証されます**。

**両方のタブに、画像を差し替えた記事を渡します。** 詳細タブだけに渡していたため、
一覧タブのカードではドロップしたサムネイルが壊れて出ていました。差し替えの仕組みは
§7-3「本文の `blob:` を通す」も必要です。

### 検証のタイミング

**ダウンロードボタンを押したときに一括で検証します。** 執筆中は警告を出しません。

**画像の存在確認も押したときに行います。** 執筆中に確かめると、ファイル名を1文字打つたびに存在しないパスへの要求が飛びます。押してから読み込みの結果を待つぶんダウンロードが少し遅れますが、執筆中は何もしません。

テンプレートの値が空である以上、常時検証すると起動直後から必須項目の欠落が3件出続けます。それに慣れてしまうと、後から出た本当の間違いを見落とします。

なお日付の形式違反は、**プレビューを見れば気づけます**。`ArticleDetail` が日付を描画するため、`2026/08/23` と書けばプレビューに `0年undefined月undefined日` が出ます。

### 2つのダウンロードボタン

| ボタン | 検証 | ファイル名 | 押した後 |
| --- | --- | --- | --- |
| **本番ダウンロード** | 必須。エラーがゼロでないと出せない | `2026-08-23-記事タイトル.md` | そのまま留まる |
| **下書きダウンロード** | しない | `_2026-08-23-記事タイトル.md` | そのまま留まる |

#### ファイル名の生成

日付とタイトルを自動連結します。`date` はフロントマターの値を使います。

- ファイルシステムで使えない文字（`/ \ : * ? " < > |`）を除去
- 空白をハイフンに変換
- 長すぎる場合は切り詰め
- 日本語はそのまま許容

#### 本番ダウンロード後の挙動

**編集内容はそのまま残します。** 白紙に戻す・退避する・復元する、のいずれも行いません。

出した直後に typo に気づいたらその場で直して出し直せます。次の記事に移るときは自分で消せばよく、消す操作より消えたものを取り戻す操作のほうが高くつきます。

ダウンロードした md は自分で `src/articles/` に置くまで公開されません。画像も「以下の画像を配置してください」の案内が残っている必要があるため、ここでは畳みません。

**投稿（`github` あり）は別です。** 押した時点で公開が済んでいるので、成功したときは雛形に戻します（§15 投稿した後）。

### 自動保存

入力のたびに localStorage へ保存します。ボタンを押す必要がないため、保存忘れが原理的に起きません。

**保存先は `storageKey` で分けます。**

```
as-studio-draft:my-blog
as-studio-draft:another-site
```

`vite dev` はどのプロジェクトでも既定で `http://localhost:5173` を使い、localStorage はオリジン単位です。プロジェクトを順番に開発すると**下書きが混ざります**。`storageKey` 未指定でも既定値で動きますが、複数プロジェクトで使う場合は指定を推奨します。

デバイス間の同期は行いません。同一デバイスでの編集のみを対象とします。

#### 画像は日付のフォルダに入れる

ドロップした画像の名前に、記事の `date` から作ったフォルダを付けます。

```
public/article_imgs/2026/10-12/0_1.png
```

`date: 2026-10-12` なら `2026/10-12/` です。**年で分け、その下を月日で分けます。**

**なぜ分けるか**：`imageDir` は記事ごとではなく**全体で1つの名前空間**です。平らに置くと
`0_1.png` のような名前が別の記事と衝突し、コミットが止まります（§15）。スマホから入れると
同じような名前になりがちなので、実際に起こります。

GitHub の画面はディレクトリの一覧を1000件で打ち切るため、平らなままだと先に詰まります。
1記事あたり数件なら、分けたほうが常に全部見えます。

**`date` が `YYYY-MM-DD` で書かれていないときはフォルダを付けません。** 空のままドロップ
されることがあり、`//0_1.png` のような壊れたパスを作らないためです。

**付いた後に `date` を書き換えても、フォルダ名は追随しません。** 表示は壊れません（書かれた
パスをそのまま読むため）。気になる場合は画像名を直してください。本文の参照も一緒に
書き換わります。

### 画像

**ドラッグ&ドロップで仮登録します。アップロードは行いません。**

```
画像をドロップ
  → ブラウザ内だけの一時URL（blob）でプレビューに即反映
  → md にはファイル名だけが入る
  → Studio 上で名前を編集できる（本文と `thumbnail:` の両方が追随する）
  → 編集後の名前で画像をダウンロードできる
  → 本番DL時に「配置してください」一覧を提示
```

スマホの写真フォルダから選ぶと `IMG_1234.jpg` のような名前になるため、**その場でリネームできることが必須**です。リネーム後の名前で画像をダウンロードできるので、スマホだけで作業が完結します。

#### 画像の保存

**実体を IndexedDB に保存します。** `blob:` URL はリロードで切れるため、保存しないと
本文に名前だけが残ります。**見えなくなるだけでなく、存在確認が 404 になって投稿も
止まります。** スマホのブラウザは裏に回ったタブを勝手に捨てるので、意図せず起きます。

| | 置き場所 |
| --- | --- |
| 本文（md） | localStorage（`as-studio-draft:{key}`） |
| 画像の実体 | IndexedDB（`as-studio-images:{key}`） |

`localStorage` には入れません。文字列しか持てず、base64 にすると容量が約1.37倍になって
写真1枚で上限（数MB）を超えます。

**`Blob` をそのまま入れ、名前は自分で持ちます。** IndexedDB の構造化クローンは実装に
よって `File` を `Blob` に落とすため、名前を往復させると環境ごとに結果が変わります。
名前は md に書く名前であって `File` の名前ではないので、これで足ります。

##### 消すのは明示的なときだけ

- **空のときは保存しません。** 開いた直後は画像が0件なので、無条件に書くと復帰する前に
  保存済みを消します
- 復帰の途中でドロップされた分も上書きしません
- 捨てるのは**投稿の成功時**と**「新しく書く」**のときだけです。持ち越すと次の記事の
  コミットに混ざり、リロードでも戻ってきます

##### 保存できなかったら伝える

プライベートブラウジングや容量超過では書けません。**黙って失敗すると「リロードしても
残る」と誤解したまま書き続けることになる**ため、画像欄に出します。

## 10. スタイル

### 同梱範囲

**そのまま公開できる完成度**まで作り込みます。

- 記事のタイポグラフィ（見出し階層・行間・余白）
- リスト・表・引用・コードブロック
- 一覧のグリッド
- Studio の2ペインレイアウト
- レスポンシブ

`classNames` を一切渡さなくても読める記事になることが目標です。

```tsx
// 新規プロジェクトで必要な全コード（Tailwind v4 なら styles.layer.css）
import "@fififuchun/article-system/styles.css";
<ArticleDetail article={article} />
```

### クラスの付き方

`as-` 接頭のデフォルトクラスを**常時付与**し、`classNames` は**追記**します。

```
classNames 未指定:              <h2 class="as-heading">
classNames={{heading:"my-h"}}:  <h2 class="as-heading my-h">
```

`styles.css` の import は任意です。読み込まなければ `as-` クラスは無害なただの文字列になるため、**従来どおり全部自分で書く**運用もそのまま成立します。Tailwind のユーティリティクラスも追記で効きます。

### 詳細度の2条件 ★重要

```css
/* Before — 利用側と同点になり、CSSの定義順で勝敗が決まる */
.as-heading { font-size: 1.5rem; }                    /* (0,1,0) */

/* 詳細度0。利用側のクラスには必ず負けるが、要素リセットにも負ける */
:where(.as-heading) { font-size: 1.5rem; }            /* (0,0,0) */

/* After — リセットには勝ち、利用側のクラスには必ず負ける */
html body :where(.as-heading) { font-size: 1.5rem; }  /* (0,0,2) */
```

**すべてのセレクタについて、次の2つを守ります。**

| | 条件 | 書き方 | 保証されること |
| --- | --- | --- | --- |
| 1 | **クラス相当の桁を0にする** | `:where()` で包む | 利用側が `classNames` で渡したクラス（0,1,0）に必ず負ける |
| 2 | **型セレクタを2つ以上にする** | `html body` を前置する | 要素1つのリセット（0,0,1）に必ず勝つ |

どちらも**読み込み順に関係なく**成立させるためです。順序に頼ると Vite のコード分割や HMR で勝敗が変わり、「昨日は効いていたのに今日は効かない」が起きます。

**詳細度は左から順に比べるので、型セレクタを何個積んでもクラス1つには勝てません。** だから1と2は両立します。

```
(0,1,0) 利用側のクラス1つ
  ↓ 勝つ
(0,0,2) ライブラリ        ← ここに居る
  ↓ 勝つ
(0,0,1) 要素リセット（Tailwind の preflight など）
```

`html body` 自体に意味はありません。**常に成立する条件**を書いて3番目の桁を2つ上げているだけです。

#### 条件2を足した理由 ★実測

当初は条件1だけで、全セレクタが (0,0,0) でした。**Tailwind v3 を使う利用側で、Studio と記事表示が崩れました。**

preflight は要素をタグ名でリセットします。これが (0,0,1) で、(0,0,0) に勝ちます。

```css
h2 { font-size: inherit; font-weight: inherit; }   /* 見出しの階層が消える */
ol, ul { list-style: none; padding: 0; }           /* 点と番号が消える */
button { background-color: transparent; }          /* ボタンの背景が消える */
a { color: inherit; text-decoration: inherit; }    /* リンクが本文と区別できない */
```

実測した影響は**61箇所**でした。

| 内訳 | 件数 |
| --- | --- |
| 詳細度で負ける | 35 |
| `*{ border-width: 0 }` と同点で、順序で負ける | 26 |

**Studio だけでなく `ArticleDetail` / `ArticleList` も崩れていました。** トークン画面で止まるため気づいていませんでした。

なお Tailwind v3.4 は `[type='button']` のような属性セレクタを**自分で `:where()` で包んでいます**。そのため preflight 側の最大は (0,0,1) で、(0,0,2) で足ります。包んでいなければ (0,1,0) になり、条件1と両立できませんでした。

#### 条件2の例外

変数を定義する `:where(:root)` だけは前置しません。`:root` は `html` そのものなので `html body` の子孫になりません。変数は preflight と名前が衝突しないため、上げる必要もありません。

#### 分かっている天井

preflight には `input::placeholder` / `textarea::placeholder` が (0,0,2) で入っています。**プレースホルダを装飾したくなったときは (0,0,2) では同点になり、順序に依存します。** 現状ライブラリは装飾していません。

### Tailwind v4 のためにもう1つ配る ★実測

v4 は**自分の CSS をすべてカスケードレイヤーに入れます**。

```css
@layer theme, base, components, utilities;
@layer base      { /* リセット */ }
@layer utilities { /* .text-3xl など */ }
```

**層に入っていない CSS は、層の中の CSS に必ず勝ちます。詳細度は見られません。** そのため v4 のサイトで層なし版を読むと、ライブラリが**利用側のユーティリティにまで勝ってしまいます**。`classNames` が黙って効かなくなります。

v3 と v4 で手段が違うため、同じファイルでは両立できません。**v3 は本物の `@layer` を書くとビルドが止まります**（v3 は `@layer` を自分の機能として扱うため）。配布を2つに分けます。

| 読む側 | ファイル | 仕組み |
| --- | --- | --- |
| Tailwind v3 / Tailwind なし | `styles.css` | 層なし・(0,0,2) |
| **Tailwind v4** | `styles.layer.css` | `@layer components` に入る |

#### なぜ `components` の層か

v4 が**最初から順番を宣言している名前**なので、利用側の設定が一切要りません。

```
base（リセット） < components（ライブラリ） < utilities（利用側のクラス）
```

独自の層名にすると、利用側が毎回順番を宣言しないと動きません。

#### 層の順番を自分で宣言する ★重要

**層の順番は「最初に出てきた順」で決まります。** 宣言しないと、ライブラリの CSS が Tailwind より先に読まれたときに `components` が `base` より前に作られ、**リセットに負けます**（実測）。

```css
@layer theme, base, components, utilities;   /* ← 層ありファイルの先頭に書く */
@layer components { /* 中身 */ }
```

書いておけば、どちらの読み込み順でも `theme → base → components → utilities` になります。実際に v4 + Vite で両方の順序をビルドして確認しました。

**他人の層名を名乗ることになります。** それでも宣言するのは、順序依存が**静かに壊れる**ためです。宣言する順番は v4 の既定そのままなので、v4 利用者の意図と食い違いません。

#### 中身は2つ管理しない

層あり版は**ビルド時に層なし版を包んで生成**します（tsup の `onSuccess`）。包む前と1バイトも違わないことをテストで固定しています。違うのは版の印1行だけです。

#### 取り違えを実行時に知らせる

v4 で層なし版を読むと**エラーも例外も出ません。** 渡したクラスが黙って無視されるだけです。

`--as-stylesheet` という印を `:root` に置き（層あり版では `layer`、層なし版では `plain`）、実行時に次の2つが揃ったときだけ `console.warn` を1回出します。

1. 本物のカスケードレイヤーが使われている（`base` と `utilities` の両方がある）
2. 印が `plain`

v3 は本物の層を一切出さないため、v3 では成立しません。版が分からないときは黙ります（CSS 自体が未読込のときに層の話で混乱させないため）。**誤検出するより、気づけないほうを選んでいます。**

**両方のファイルを読み込んでしまった場合も同じ警告で拾えます。** 層なしが勝って印が `plain` になるためです。

#### v3 では「丁寧さ」を提供できない

v3 では層が使えないため、**利用側がタグ名だけで書いた CSS（`h2 { }`）にライブラリが勝ってしまいます**。回避する手段がないので受け入れます。利用側はクラスを足せば勝てます（`.article h2 { }` なら (0,1,1)）。

#### 対応ブラウザの宣言

`package.json` の `browserslist` に宣言します。**ビルドがこれを読んで検証する仕組みは入れていません**（esbuild は browserslist を読みません）。「ここを下回る環境は対象にしていない」という表明であり、README の記載とずれないことだけをテストで固定しています。

```
chrome >= 108 / edge >= 108 / safari >= 15.4 / firefox >= 101
```

数字を決めているのは `100dvh`（Chrome 108）と `@layer`（Safari 15.4）です。

| 根拠 | 確認状況 |
| --- | --- |
| `@layer` = Chrome 99 / Safari 15.4 / Firefox 97 | MDN の互換表で確認済み |
| `100dvh` = Chrome 108 | 確認済み |
| `100dvh` の Safari / Firefox の版 | **未確認。** Firefox 101 は概算 |

#### 構造的な弱点

- `!important` 付きの宣言は**層の順番が逆転**します。v4 の `base` には1箇所あります（`[hidden]`）。ライブラリは使っていないので今は影響しませんが、v4 が `!important` を増やすと層あり版が負ける箇所が出ます
- `@layer` は Chrome 99 / Safari 15.4 以降。**未対応ブラウザでは層の中身が丸ごと無視されます。** v4 自体がもっと新しいブラウザを要求するため、v4 利用者には実害がありません

### Studio コードの分離について

`./studio` エントリポイントへの分離は**後回し**とします。

現在のバンドル 307KB のうち 156KB は react-markdown 系で、これは読者向けの `ArticleDetail` が使うため Studio の有無に関わりません。Studio 固有の増分は十数KB程度（gzip 後は数KB）と見積もられ、個人ブログの規模では影響がありません。Studio が育った段階で対応します。

## 15. GitHub 連携

`github` prop を渡すと、Studio はダウンロードの代わりに**リポジトリへ直接コミット**します。渡さなければ v1 のまま（ダウンロードのみ）動きます。

### 設定

```ts
interface GitHubConfig {
  repo: string;       // "owner/name"
  branch?: string;    // 既定 "main"
  mdDir?: string;     // 既定 "src/articles"
  imageDir?: string;  // 既定 "public/article_imgs"
}
```

既定値は §2 の構成に合わせています。`imageBasePath` は**表示用のURLパス**であり、リポジトリ上の置き場所とは別物です。両方を指定する必要があります。

### 認証は Fine-grained PAT

利用者が GitHub で発行した **fine-grained personal access token** を画面に貼ります。トークンが無ければ**編集画面を出しません**。

これが §13 の「Studio を本番に置くならホスティング側の認証を強く推奨」の代わりになります。書き込み権限は GitHub 側（トークンのスコープ）で決まるため、ライブラリが認可を持つ必要がありません。

利用者に用意してもらうトークン：

- **Repository access** — 対象のリポジトリだけ
- **Permissions → Contents: Read and write** — これだけで足ります
- 有効期限は GitHub 側で設定してもらう

### なぜ GitHub App のログインにしないのか ★調査済み

`https://github.com/login/oauth/access_token`（`code` をトークンに交換するエンドポイント）に **CORS が無いため、ブラウザから叩けません**。GitHub App の SPA クライアント対応は Preview かつ **Paused** で、時期の見通しがありません。

- GitHub ドキュメント: 「CORS pre-flight requests (OPTIONS) are not supported at this time」
- GitHub 側の回答（2025-07-15）: PKCE は追加済み、CORS は作業中、client secret を外す予定は無い
- ロードマップ [github/roadmap#1153](https://github.com/github/roadmap/issues/1153): Preview / Paused

一方 **`api.github.com` は CORS 対応**（`Access-Control-Allow-Origin: *`）なので、**コミット処理はブラウザだけで完結します**。詰まるのはログインの1手だけでした。

バックエンドを1つ持てばログイン方式にできますが、このライブラリは**利用側にサーバーを要求しない**方針を採ります。SPA 対応が再開したら乗り換えます（§16）。

### トークンの置き場所

**sessionStorage** に置きます。リロードしてもう一度貼らずに済み、タブを閉じれば消えます。**トークンは画面に出しません** — 入力欄は `type="password"` にし、保存後は再表示しません。

なお**下書き本文は localStorage に残ります**（§9）。トークンの寿命を短くしても、書きかけの記事が端末に残る点は変わりません。

### 貼られたトークンは即座に確かめる

2回の読み取りで確かめてから受け入れます。

1. `GET /repos/{repo}` — リポジトリが見えること（401 / 404 を切り分ける）
2. `GET /repos/{repo}/commits?per_page=1` — **Contents 権限が付いていること**

**1つ目だけでは足りません。** この応答の `permissions` は**所有者のリポジトリ権限**を映すもので、
**トークンに付いた権限ではありません**。Contents を付け忘れたトークンでも `push: true` で
通ってしまいます（実地確認で踏みました）。Contents を要求する呼び出しを実際に1つ試します。

**書き込みだけを試す手段はありません**（試せば書いてしまう）。確かめられるのは読み取りまでです。
とはいえ「Contents を付け忘れた」がいちばん多い間違いで、それはここで捕まえられます。

空のリポジトリは 2 が 409 を返しますが、トークン自体は通っているので受け入れます。

### コミットは Git Data API で1コミット

Contents API は 1リクエスト＝1ファイル＝1コミットです。md と画像を順に置くと、途中で失敗したとき**画像だけ、あるいは画像の無い記事だけが公開状態で残ります**。取り消すには別のコミットが要ります。

Git Data API なら blob → tree → commit → ref の順に組み立て、**最後の ref 更新までリポジトリには何も現れません**。

1. `GET .../git/ref/heads/{branch}` — 最新のコミットSHA
2. `GET .../git/commits/{sha}` — そのコミットのツリーSHA（`base_tree` に要る）
3. `GET .../git/trees/{sha}?recursive=1` — 衝突の確認
4. `POST .../git/blobs` — md と画像それぞれ（画像は `encoding: "base64"`）
5. `POST .../git/trees` — `base_tree` に現在のツリー、`tree` に追加分
6. `POST .../git/commits` — メッセージは `記事を追加: {title}`
7. `PATCH .../git/refs/heads/{branch}` — ここで初めて公開される。`force` は付けない

### 衝突検出は GitHub の最新ツリーを見る

`articles` は**ビルド時のスナップショット**です。同じセッションで先にコミットした記事はそこに載っていないため、`articles` だけで判定すると**直前に自分が書いた記事を黙って上書きします**。

コミット時に最新のツリーを1回引き、同名ファイルを検出します。`base_tree` に渡すツリーSHA は親コミットから得られますが、**中身の一覧は別途 `GET .../git/trees/{sha}?recursive=1` が要ります**。衝突していたら、その時点で止めて何も書きません。

### 応答をキャッシュさせない ★重要

すべての呼び出しを `cache: "no-store"` で出します。

ブラウザが GitHub の応答を再利用すると、**古い先端の上にコミットを作って ref を
早送りできなくなります**（`Update is not a fast forward`）。最新ツリーによる衝突検出も
古いまま返るため効かなくなります。1回目のコミットは通り、2回目で失敗します
（実地確認で踏みました）。

### 失敗したとき

通信エラー、トークンの失効や取り消し（401）、権限不足（403）、他人が先に push して ref が進んだ場合（422）など。GitHub が返す英語の文言（`Git Repository is empty.` / `Resource not accessible by personal access token` / `Update is not a fast forward`）では何をすればよいか分からないため、
**どの段階で止まったかと、次にすることを添えて**出します。

- 検証エラー欄に理由を出します
- 同じ場所に **「代わりにダウンロード」ボタン**を出します。書いたものを必ず持ち帰れるようにするためです
- **黙ってダウンロードに落とすことはしません。** コミットされたと勘違いされます
- 401 のときは理由とあわせて **「トークンを入れ直す」** を出し、**押されたときに破棄します**。先に破棄すると編集画面が関門に戻り、書いたものをダウンロードする機会が消えます

### ボタンの出しわけ

`github` 設定とトークンの有無で**ラベルだけ**が変わります。ボタンの数と位置は変えません。

| | 本番 | 下書き |
| --- | --- | --- |
| `github` なし | 本番ダウンロード | 下書きダウンロード |
| `github` あり・トークンあり | **投稿** | 下書きダウンロード |

**下書きはコミットしません。** 押すたびにコミットが積み上がり、公開リポジトリなら書きかけが誰でも読めるためです。下書きの保存は localStorage の自動保存が担います。

### 投稿の前に確認を取る

**ボタンの文言は「投稿」です。「コミット」ではありません。** `commitArticle` はブランチの
ref まで更新するため、押した時点でリポジトリに入って公開されます。「コミット」だと
手元に積んだだけに見えます。

押すと `window.confirm` で一度止めます。**この画面に取り消す手段がないためです。**

```
「夏の更新」を投稿します。

ファイル: 2026-08-23-夏の更新.md
画像: 2 件

投稿するとリポジトリに入って公開されます。この画面からは取り消せません。
```

何が出ていくのかを並べます。「よろしいですか」だけでは判断できません。

**確認は検証を通った後に出します。** 直すところが残っているのに確認されても答えようが
ありません。**ダウンロードでは出しません** — 取り返しがつきます。

### 投稿した後

成功したときだけ**雛形に戻します**。画像欄も畳みます。

- 投稿が済んだ記事を残すと、次を書くたびに手で消すことになります
- 投稿済みの画像を持ち越すと、次のコミットで同名衝突になります（§15 画像）

**失敗したときは残します。** 書いたものを取り戻す手段がなくなります。

雛形の `slug` には、**このセッションで投稿した slug も数えます**。`articles` はビルド時の
スナップショットなので、投稿した記事は載っていません。数えないと同じ日の2本目が
同じ URL になります（§3）。

### 画像

投稿には**ドロップした画像も同じコミットに含めます**。

**同名の画像が `imageDir` に既にあれば止めます。** 上書きすると、その画像を使っている
**別の記事**が壊れます。取り消しもできません。Studio でリネームしてから出し直します。

ドロップした画像は日付のフォルダに入るため（§9 画像）、通常は衝突しません。手で書いた
ファイル名や、フォルダを外した場合に起こりえます。

`imageDir` に置かれるため、「以下の画像を配置してください」の案内は出しません。

画像の存在確認（§6）も、ドロップした画像については不要になります。手書きのファイル名だけを確認します。

ただし**編集中の画像は依然としてブラウザ内の blob** です。コミット前にリロードすれば消えます（§17）。

### 実地確認

テストは `fetch` をスタブするため、**本物の GitHub と通信できることは証明しません**。`demo/` に「GitHub 連携」ページを置き、トークンと `repo` を画面から入力してコミットまでを目で確かめます。リポジトリには秘密を置きません。

デモの既存ページは `github` を渡さないままにします。既定の挙動を見せる場としての役割を変えないためです。

## 16. まだ対応していないこと

**0.3.0 時点で未実装です。** 「将来やる」ではなく、**いま使うと困る点**として書きます。

### 16-1. 同じ日に同じタイトルの記事を2本出せない ★いちばん困る

ファイル名が `{date}-{title}.md` なので、**同じ日に同じタイトルで書くと衝突して止まります**。

```
ファイル名 2026-08-23-夏の更新.md は既存の記事と重複しています。
```

`slug` は自動で `-2` が付くようになりましたが（§3。同じセッションで投稿した分も数えます。§15 投稿した後）、**ファイル名は変わりません**。

**なぜ止めているか**：同名で書き出すと既存の記事が物理的に上書きされて消えるためです（§6）。
取り消せません。

**直すなら**：空いている名前（`2026-08-23-夏の更新-2.md`）を自動で選んで通します。
ただし**これだけ入れると、同じ記事を直すたびに `-2` `-3` が増えます**。
「別の記事が偶然同名」なのか「同じ記事の書き直し」なのかを機械は区別できないためです。
16-2 と対にするのが自然です。

### 16-2. 既存記事を編集できない（新規作成専用）

書き直すと**別の記事として増えます**。既存の記事を開いて直す手段がありません。

**直すなら**：`articles` から選んで開き、`latestUpdate` を今日にし、同じファイル名に
コミットを重ねます。

**決めることが残っています**（推測で実装しない）：

- 既存記事をどう選ぶか（一覧から選ぶ／ファイル名を入力する）
- 開いたとき `latestUpdate` を自動で今日にするか
- 下書きの保存先を記事ごとに分けるか（いまは `storageKey` ひとつ。§9）
- **更新は同じファイル名への上書きになる。** §6 の「上書きは必ず止める」とどう両立させるか
- 更新時に `slug` を変えさせるか（変えると公開済みの URL が切れる。§3）

最後の2つは、これまで「止める理由」として積み上げてきたものと正面からぶつかります。

### 16-3. 下書きがデバイス間で共有されない

下書きは localStorage に入るだけで、コミットしません（§15）。PC で書きかけたものを
スマホで続けられません。

**なぜコミットしないか**：押すたびにコミットが積み上がり、公開リポジトリなら書きかけが
誰でも読めるためです。

### 16-4.（解決済み）編集中の画像がリロードで消える

IndexedDB に保存して復帰させるようにしました（§9 画像の保存）。
**保存できない環境では今までどおり消えます。** その場合は画像欄に出します。

### 16-5. GitHub App のログインが使えない

`login/oauth/access_token` に CORS が無く、ブラウザから `code` を交換できません。
SPA クライアント対応は Preview かつ Paused です（§15）。

いまは fine-grained PAT を画面に貼る形です。**再開したらログイン方式に乗り換えます。**

### 16-6. 読者のバンドルに Studio のコードが入る

`ArticleStudioRoute` を置くと、執筆ツールのコードも読者に配られます（未圧縮で25KB前後、
gzip で8KB程度）。遅延読み込みにせず実装を単純に保つ判断をしました（§9 設置方法）。

**直すなら**：`./studio` を別のエントリポイントに分けます。

## 17. 意図的に受け入れている制約

設計上わかっていて許容している点です。実装で解決しようとしないでください。

| 制約 | 理由 |
| --- | --- |
| `<h1>` を持たない | 記事の見出しが `<h2>` から始まるのを正常とする |
| デバイス間で下書きが同期されない | 同一デバイスでの編集のみを対象とする。下書きは GitHub にもコミットしない（§15） |
| 未来日の typo を検出できない | 未来日を許可する方針のため |
| ファイル名を変えれば検証を回避できる | 別の手段で対処する |
| ファイル名と `date` がずれうる | 中身（フロントマター）を信じる。ファイル名は付属情報 |
| ファイル名の大文字小文字を区別する | `A.md` と `a.md` は別ファイルとして扱う。大文字小文字を区別しないファイルシステムでは衝突しうるが、検出しない |
| `staff` を毎回入力する | 記憶させない |
| Tailwind v3 では利用側のタグ指定に勝ってしまう | preflight（0,0,1）に勝つには (0,0,2) が必要で、同じ桁の利用側の指定も巻き込む。v3 には層が無いため回避できない（§10）。クラスを足せば利用側が勝つ |
| 層あり版と層なし版を取り違えても止まらない | v4 で層なし版を読んだ場合は実行時の警告のみ（§10）。CSS だけでは判定できない |
| 例外を投げても漏洩は取り消せない | 放置期間を最短にするための警報として機能させる |

## 18. 共有したときのサムネイル（OGタグ）

記事の URL を X や LINE に貼ったとき、サムネイル付きのカードを出します。

### なぜ普通には出ないのか ★調査済み

**クローラーは JavaScript を実行しません。** URL を貼られると、X のサーバーが
その URL を1回取りに行き、返ってきた HTML の文字列から `og:` のタグを読みます。
ブラウザを開くわけではありません。

SPA が返す HTML は、どの記事 URL でも同じ1枚です。実際に測りました。

```
$ curl http://localhost:5199/article/2026-10-10-日本語の記事

記事タイトルの出現回数: 0
画像パスの出現回数:     0
og: で始まる行:         0
```

`<div id="root"></div>` は空で、記事は後から JavaScript が描き込んでいます。
`react-helmet` のように React からタグを足す仕組みも**効きません。** 足すのは
React が動いた後であり、クローラーはもう帰っています。

**ハッシュルーティングでは原理的に不可能です。** `#` から後ろはサーバーに
送られないため、`#/article/夏` と `#/article/秋` はサーバーから見て同じ URL です。
読者向けを実パスにしているのはこのためでもあります（§9 設置方法）。

### 直し方

**ビルド時に記事ごとの HTML を書き出します。**

```
dist/
├── index.html
├── article/
│   ├── 2026-10-12/index.html   ← この記事のタグが入ったコピー
│   └── 2026-10-10/index.html
└── assets/...
```

中身は `dist/index.html` の `<head>` にタグを入れただけのコピーです。
**`<script>` はそのまま残します。** 人間が開いたときは今までどおり React が
起動するため、挙動は変わりません。

### ライブラリの中で完結させる ★境界線を越える判断

フェーズ11では**読者向けページを出来合いにしない**と決めました。理由は
「`<title>` と OG タグを記事ごとに出すには、利用側が `article` を手元に持つ
必要がある」ことでした（§9 設置方法）。

**この §18 はその線を逆向きに越えています。** 利用側に後処理を書かせず、
ライブラリが出力先に HTML を書き出します。越えるにあたって、線を引いた
理由そのものである危険を設計で潰しました。

| 危険 | 潰し方 |
| --- | --- |
| 記事の探し方が本体とプラグインで二重管理になる | slug の決め方を `resolveSlug` に1か所だけ置き、`createArticles` とプラグインの両方が呼ぶ |
| 壊れても共有されるまで気づけない | 黙って諦めずビルドを止める（下記） |
| Vite のバージョンに追従し続ける必要がある | `vite` に依存しない。`configResolved` と `closeBundle` だけを持つ素のオブジェクトを返す |

### 2つに分かれている

| | 中身 | 置き場所 |
| --- | --- | --- |
| タグの文字列を作る | `Article` → `<meta ...>` | `buildArticleHead`（ブラウザ側の入口からも使える） |
| HTML として書き出す | `dist/article/{slug}/index.html` | `@fififuchun/article-system/vite` |

**配布を分けています。** 書き出す側は `node:fs` を使うため、読者のバンドルに
混ざるとブラウザ向けのビルドが解決できずに壊れます。`src/vite` の外で
`node:` を import しないことをテストで固定しています。

```ts
// vite.config.ts
import { articleOgTags } from "@fififuchun/article-system/vite";

export default defineConfig({
  plugins: [
    react(),
    articleOgTags({ siteUrl: "https://example.com", path: "/article/:slug" }),
  ],
});
```

### 出すタグ

```html
<title>夏の更新</title>
<link rel="canonical" href="https://example.com/article/2026-10-12">
<meta name="description" content="…">
<meta property="og:type" content="article">
<meta property="og:title" content="夏の更新">
<meta property="og:description" content="…">
<meta property="og:url" content="https://example.com/article/2026-10-12">
<meta property="og:image" content="https://example.com/article_imgs/2026/10-12/0_1.png">
<meta property="og:site_name" content="私のブログ">
<meta name="twitter:card" content="summary_large_image">
<meta property="article:published_time" content="2026-10-12">
<meta property="article:modified_time" content="2026-10-13">
```

`canonical` を出すのは、末尾スラッシュの有無で同じ記事が2つの URL で開ける
ためです。どちらが本体かを1つに決めます。

**サムネイルが無ければ `og:image` を出さず、`twitter:card` も `summary` に
落とします。** 画像の無いまま大きいカードを指定すると、各サービスで崩れて出ます。

### `siteUrl` が必須な理由

**`og:image` は絶対URLでなければ無視されます。** ドメインはライブラリから
分からないため、渡してもらう必要があります。`http://` か `https://` で
始まっていなければ例外を投げます。

URL は手で文字列を繋がず `URL` に任せます。繋ぐと、`imageBasePath` 自体が
絶対URL（CDN）のときに `https://site/https://cdn/...` を作ります。**実際に
デモで踏みました。** `URL` なら絶対URLはそのまま、`//` から始まるものには
scheme が付き、日本語は percent-encoding され、すでに `%XX` の部分は二重に
encode されません。

画像は**表示に使うのと同じ `resolveImageSrc` を通してから**絶対URLにします。
別の判定を書くと、プレビューに出ている画像とカードの画像が食い違います。

### 属性値を escape する ★重要

`title: 夏の"更新"` と書かれるだけで HTML が壊れます。属性は `"` で囲むため、
escape しなければタグを閉じて別の要素を書き込めます。`&` `"` `'` `<` `>` を
落とします。

### 説明文の決まり方

**常に本文の冒頭から作ります。** フロントマターに説明文の項目は持ちません。

項目を増やすほど記事を書くたびに書くことが増えます。フロントマターは最小に
保つ方針のため、`description` を受ける案は取りませんでした（書かれていても
他の独自キーと同じく黙って通ります）。

マークダウンの記号を落として1行に畳み、120文字で切ります。
**アンダースコアは落としません。** `0_1.png` のようなファイル名が本文に
出てくるため、`_強調_` を拾うより壊さないほうを選びました。

### 元のタグを引き継がない

記事用のコピーからは、元の `index.html` にあった `<title>` と
`og:` / `twitter:` / `description` を消します。

- `<title>` が2つあると、**先に書かれたほうが使われます**
- `og:` が重複すると、どちらが拾われるか分かりません

**どちらも静かに間違った結果になります。** トップページの `index.html`
そのものは変更しないので、トップ用のタグはそのまま残ります。

### 止めるとき

OGタグは**誰かが共有するまで壊れているか分かりません。** 他の機能のように
ブラウザを見れば気づけるものではないため、黙って諦めさせず例外でビルドを
止めます。

| 状況 | 理由 |
| --- | --- |
| `path` に `:slug` が無い | 書き出す先が決まらない。プラグインを作った時点で止める |
| `siteUrl` が絶対URLでない | タグは出るが無視される |
| 記事のフォルダが読めない | `articlesDir` の指定違い |
| 記事が0件 | 設定が間違っている証拠。黙って何も出さないと気づけない |
| 出力に `index.html` が無い | コピー元が無い |
| `index.html` に `</head>` が無い | タグを入れる場所が決まらない |

### ホスティング側の前提 ★実測

`/article/2026-10-12` を**`/article/2026-10-12/index.html` から返せる必要が
あります。** Vercel・Netlify・GitHub Pages はいずれも既定でそうします。

**`vite preview` はしません。** SPA のフォールバックが先に効き、ルートの
`index.html` が返ります。ローカルで確かめるときは末尾にスラッシュを付けます。

```
$ curl -s http://localhost:4173/article/2026-10-12/ | grep og:
```

デプロイ後は、実際の URL を `curl` して `og:` が返ることを確かめてください。
