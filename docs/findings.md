# 解析で分かったこと・注意点

コードを読んで判明した仕様上の制約と、実際に踏みうる落とし穴をまとめます。
「そういう設計だ」と納得して使う分には問題ないものも含めて、明示しておく価値があるものを挙げています。

重要度の目安: **要注意** = データやURLが壊れうる / **把握しておく** = 挙動を知らないと戸惑う / **改善候補** = 今は困らないが将来効いてくる

---

## 要注意

### 1. `id` は不安定 — 記事を過去日付で追加すると既存 URL が全部ずれる

`createArticles` は `date` 昇順にソートした**後の配列 index** を `id` にしています。

```ts
.sort((a, b) => new Date(a.date).getTime() - new Date(b.date).getTime())
.map((article, index) => ({ ...article, id: index }))
```

README の想定どおり `/blog/:id` でルーティングすると、`id` がそのままパーマリンクになります。ここで**既存記事より古い日付の記事を後から追加すると、その記事以降の `id` がすべて +1 され、公開済み URL が全部別の記事を指すようになります**。

```
初期状態:              後から 2024-01-01 の記事を追加:
id=0  2024-03-15        id=0  2024-01-01  ← 新規記事
id=1  2024-08-20        id=1  2024-03-15  ← /blog/0 だった記事
id=2  2025-01-10        id=2  2024-08-20  ← /blog/1 だった記事
```

既存記事の `date` を修正した場合も同じことが起きます。ブックマーク・外部リンク・検索エンジンのインデックスがすべて破綻します。

**対処案**: フロントマターに `slug` を追加してそれを URL に使い、`id` は表示順の管理だけに留める。実装は `types.ts` に `slug` を足し、`createArticles` で `data.slug ?? String(index)` を埋めるだけで済みます。

### 2. `date` / `latestUpdate` が空・不正だと画面に `0年undefined月undefined日` が出る

日付は `split("-").map(Number)` で分解していますが、値が空文字のときの挙動を実際に確認しました。

```
"".split("-").map(Number)  →  [0]
→ year=0, month=undefined, day=undefined
→ 描画結果: "0年undefined月undefined日"
```

`createArticles` は欠損フィールドを `""` で埋めるため、**フロントマターに `latestUpdate` を書き忘れただけで、例外も警告も出ないまま本番画面に `0年undefined月undefined日` が表示されます**。キー名の typo（`lastUpdate` と書いてしまう等）でも同様です。

`ArticlePreview` を README どおり `defaultValue` なしで置いた場合、**初期表示がまさにこの状態**になります（デモは `SAMPLE` を渡しているため隠れています）。

**対処案**: `createArticles` で必須フィールドの欠損を `console.warn` する、または描画側で日付が不正なときは日付ブロックごと出さない。

### 3. `date` が不正な記事があるとソート順が不定になる

比較関数が `NaN` を返すと、`Array.prototype.sort` の結果は仕様上保証されません。実測でも壊れます。

```
入力:  ["x", "2024-01-01", "2023-01-01"]
結果:  x, 2023-01-01, 2024-01-01     ← "x" が先頭に居座る
```

`date: 2025/06/01`（スラッシュ区切り）のような書き間違いでも `new Date()` は環境によって解釈が変わり、順序が揺れます。並び順が狂うと `id` も狂うので、1 の問題と連鎖します。

### 4. `<div>` が `<p>` の中に入る — SSR で HTML 構造が壊れる

`ArticleDetail` の `components` マップで、段落は `<div class="paragraph"><p>…</p></div>`、画像は `<div class="image"><img></div>` に置き換えられます。マークダウンでは**画像だけの行も段落として扱われる**ため、実際の出力はこうなります。

```html
<div class="article-paragraph">
  <p>
    <div class="article-image"><img src="..."></div>   ← p の中に div
  </p>
</div>
```

`<p>` の中に `<div>` は HTML の仕様違反です。クライアントサイドレンダリングでは DOM API 経由で構築されるため見た目は問題なく動きますが、

- React の開発モードで `validateDOMNesting` 警告が出る
- **SSR / SSG では出力された HTML 文字列をブラウザが再パースする際に `<p>` が自動で閉じられ、DOM 構造がサーバーと食い違ってハイドレーションエラーになる**

現状は Vite の CSR 前提なので顕在化していませんが、Next.js 等に持ち込むと踏みます。

**対処案**: `p` のカスタムコンポーネントで子に画像が含まれる場合は `<p>` でラップしない、または段落のラッパーを `<div>` ではなく `<p className={...}>` 一段にする。

### 5. `npm link` 時に React が二重ロードされうる

`demo/node_modules/@fififuchun/article-system` はリポジトリルートへのシンボリックリンクです。そしてルートの `node_modules` には **React 19.2.6**、`demo/node_modules` には **React 18.3.1** が入っています。

```
ルート:  react 19.2.6   （react-markdown の peer として自動導入されたもの）
demo:    react 18.3.1
```

シンボリックリンク経由で `dist/index.js` の `import "react"` が実体パス基準で解決されると、ライブラリ側は React 19、アプリ側は React 18 を掴み、`ArticlePreview` の `useState` が「Invalid hook call」で落ちます。

**デモが動いているのは `@vitejs/plugin-react` が `resolve.dedupe: ["react", "react-dom"]` を自動設定しているおかげ**であり、ライブラリ側が保証している性質ではありません。他のバンドラや素の Vite 設定で `npm link` した利用側では発生しえます。

**対処案**: 利用側の `vite.config.ts` に `resolve.dedupe: ["react", "react-dom"]` を書く旨を README に追記する。あるいはルートで React を明示的に devDependency として React 18 に固定する。

## 把握しておく

### 6. 一覧は「古い順」に並ぶ

`createArticles` は昇順ソートなので、`ArticleList` にそのまま渡すと**最も古い記事が左上**に来ます。ブログ用途では新しい順が普通なので、逆順にしたい場合は利用側で反転します。

```tsx
<ArticleList articles={[...articles].reverse()} … />
```

`.reverse()` は破壊的なのでスプレッドでコピーしてから呼ぶ必要があります。`id` は保持されるので URL は壊れません。

### 7. `imageBasePath` は単純な文字列結合

```ts
src={`${imageBasePath}${src}`}
```

パス結合ではなく連結です。したがって、

- `imageBasePath` の末尾スラッシュを忘れると `/article_imgsart_0.webp` になる
- マークダウンに `![](https://example.com/a.png)` と書くと `/article_imgs/https://example.com/a.png` になり、**外部画像は使えない**
- デモはこれを逆手に取り、`imageBasePath` に `https://placehold.co/800x400/e8e8e8/999999?text=` を渡してファイル名をクエリ文字列に流し込んでいる

### 8. サムネイルは未指定でも必ず `<img>` が出る

`thumbnail` が空文字でも `<img src="/article_imgs/">` が無条件に描画され、ブラウザの壊れた画像アイコンが出ます。サムネイルなしの記事は想定されていません。

### 9. フロントマターは YAML ではない

自前実装（18行）で、`key: value` を1行ずつ拾うだけです。

| 記法 | 結果 |
| --- | --- |
| `title: 記事：その1` | ✔ 最初のコロンで切るので値中のコロンは安全 |
| CRLF 改行 | ✔ 正しく処理される（`trim()` が `\r` を除去） |
| `title: "記事"` | ✘ **引用符が値に含まれたまま**（`"記事"` になる） |
| `tags: [a, b]` | ✘ 文字列 `"[a, b]"` として入る（配列にならない） |
| 複数行の値 | ✘ 2行目以降は無視される |
| `# コメント` | ✘ コロンが無い行として黙って読み飛ばされる |
| 未知のキー | ✘ パースはされるが `Article` に載らないため捨てられる |

「引用符で囲む」は YAML の習慣なのでつい書きがちですが、ここでは逆効果です。

### 10. `classNames` を指定できるのは h2 / h3 / h4 / p / img だけ

リスト、表、引用、コードブロック、太字、リンク、そして `#`（h1）は react-markdown のデフォルト出力（素の `<ul>` `<table>` `<h1>` …）になり、クラスは付きません。スタイルを当てるには利用側で子孫セレクタを使います。

```css
.article-wrapper ul { … }
.article-wrapper table { … }
```

### 11. 見出しが `<h2>` ではなく `<div>` で出力される

ブラウザ標準スタイルの打ち消しが不要になる利点がある一方、見出しレベルの意味情報が DOM から失われます。スクリーンリーダーの見出しジャンプが効かず、検索エンジンも文書構造を認識できません。記事系サイトでは無視しにくいトレードオフです。

### 12. 単一改行が `<br>` になる

`remark-breaks` により、マークダウン標準（空行のみが段落区切り、単一改行は無視）とは異なる挙動になります。日本語の執筆感覚には合いますが、既存のマークダウン資産を持ち込むと改行だらけになる可能性があります。

### 13. 生 HTML は無効

`rehype-raw` を入れていないため、マークダウン中の `<div>` などはエスケープされて文字列として表示されます。裏を返せば、**記事経由の XSS は構造的に防がれています**。信頼できない書き手が記事を書く運用でも比較的安全です。

### 14. UI 文言が日本語でハードコードされている

- 「担当：」（`ArticleDetail` のフッター、prop で変更不可）
- 「〇年〇月〇日」の日付フォーマット
- `dateLabel` のデフォルト `"最終更新日時"`（これは prop で変更可）

日本語サイト専用のライブラリです。多言語化する場合はコンポーネントの改修が必要です。

### 15. `ArticlePreview` の入力は保存されない

`useState` のみで、localStorage への保存もファイル出力もありません。リロードすると書いた内容は消えます。長文をここで書き始めるのは危険で、エディタで書いたものを貼って確認する使い方が前提です。

### 16. ファイル名は記事の識別に使われていない

`createArticles` は `Object.values()` でパスを捨てるため、`2024-03-15-first-steps.md` という命名は人間のための整理でしかありません。実際に効くのはフロントマターの `date` だけです。ファイル名の日付とフロントマターの日付がずれていても、システムはフロントマターを信じます。

## 改善候補

### 17. テスト・Lint・CI が一切ない

`createArticles` と `parseFrontmatter` は入出力が明確な純粋関数で、テストを書くコストが非常に低い部分です。上記 2・3・9 のようなエッジケースは、ここに数本テストを置くだけで回帰を防げます。`package.json` に `test` スクリプトもありません。

### 18. `package.json` の `exports` で `types` が後ろにある

```json
"exports": { ".": { "import": "./dist/index.js", "types": "./dist/index.d.ts" } }
```

`exports` の条件は**記述順にマッチ**するため、`types` は先頭に置くのが規約です。現状は `dist/index.d.ts` が `index.js` と同じ場所にあるため TypeScript が拾えており実害は出ていませんが、順序は直しておくのが無難です。

### 19. `files` フィールドがなく、npm 公開の準備はされていない

version は `0.1.0` のまま、`repository` / `license` / `description` も未設定です。現状は git clone + `npm link` 前提の私的ライブラリなので問題ありませんが、公開するなら整える必要があります。

### 20. `dist/` をコミットする運用の副作用

`ce86c36「distもビルドに含める」`でビルド成果物がリポジトリに入りました。リンク先ですぐ使える利点がある一方、

- `src` を編集して `npm run build` を忘れると、コミットされた `dist` と `src` が食い違う
- diff にビルド成果物のノイズが乗る

**対処案**: pre-commit フックで `npm run build` を走らせて `dist` の同期を強制する、もしくは公開時のみビルドする運用に戻す。

### 21. 型の React バージョンが揃っていない

ルートの `@types/react` は `^19.0.0`、`demo` は `^18.3.0` です。`dist/index.d.ts` は React 19 の型で生成されるため、React 18 の型を使う利用側で JSX 名前空間の差異による型エラーが出る可能性があります。`peerDependencies` は `react: ">=18"` と広く取っているので、型もそれに合わせるか、対応範囲を明示するのが望ましいです。

### 22. `subsubheading`（`####`）が README に載っていない

`12ec1de「####タグ追加」`で後から追加されたキーですが、README のサンプルコードの `classNames` には含まれていません。コピペで始めた利用者は `####` を書いてもクラスが当たらず戸惑います。

## 総評

**小さく、意図がはっきりしていて、読みやすいライブラリ**です。「スタイルを持たない」「ルーターに依存しない」「ビルド時に完結する」という3つの方針が最後まで一貫しており、`renderLink` による依存の切り離しや、`ArticlePreview` が `ArticleDetail` を再利用して本番と表示を一致させている点は素直に良い設計です。依存も react-markdown 系3つだけに抑えられています。

一方で弱いのは**入力の検証**です。フロントマターの欠損・typo・日付フォーマット違反がどれも無言で通過し、壊れた表示（`0年undefined月undefined日`）や壊れた並び順として本番に出てしまいます。記事の追加が「ファイルを置くだけ」である以上、置かれたファイルが正しいかを確認する層がどこにも無いのは片手落ちです。

優先して着手するなら次の3つを推します。

1. **`id` をフロントマターの `slug` ベースに切り替える**（1）— URL の破綻は後から取り返しがつかないため最優先
2. **`createArticles` にバリデーションと警告を入れる**（2・3）— 30分程度の作業で、無言の破損が可視化される
3. **`createArticles` / `parseFrontmatter` のユニットテストを置く**（17）— 上2つの修正を安全にするための土台
